1.4 「App 人格」· 像一位专业教练那样工作

FitLab 不是"数据看板"——它是一位住在你手机里的专业教练。这个人格设定会贯穿整个产品：

维度数据看板的做法（NO）FitLab 教练人格（YES）
呈现数据 "Q/H = 1.96" "⚠ 你的 Q/H 1.96 超出了健康区间 1.0-1.7——意思是大腿前肌训得比后肌多近 1 倍。这关系到膝韧带"
给计划 "做 3 组×10 次" "今天 3 组×10 次。为什么 3 组：这块肌肉的 MEV 门槛是 6 组/周，今天给 3 组、周五再 3 组刚好达标。为什么 10 次：8-12 次能同时刺激力学张力 + 代谢应激"

发现问题 "3 块肌肉低于 MEV" "诊断：3 块肌肉低于 MEV——但只有 三角肌中束 是真问题（计划里只 1 个动作带它）。另 2 块是辅助稳定肌不强求。建议下周：把侧平举从 3 组升 4 组"

1.6 计划生成方法论 · 一个好的初始计划不应需要"修复"

诚实声明 + 修订设计：之前的设计里"复盘 → 修复方案 → 应用到计划"流程有一个根本逻辑问题——如果教练给的初始计划从设计阶段就包含 MEV 缺口和平衡失衡，那这个教练就不够专业。

正确的拆分应该是：
  • 计划级问题（结构性）→ 应该在生成阶段就自检并修掉，不让用户看到
  • 执行级问题（偏差）→ 是用户没按计划做到，复盘里给修复建议
这两类问题需要不同的处理路径。下面把这事讲清楚。

1.6.1 一个"专业教练级"计划生成算法

计划生成 = 约束求解（constraint optimization）问题。不是"挑动作 + 排时间"那么简单。

输入来源
训练目标用户选（增肌/力量/耐力/健康）→ 决定 MEV/MAV/MRV 倍数
个人 MEV 系数无历史→默认 1.0× / 有历史→评估面板算出（如 1.3×）
训练频率用户选（2-5 次/周）→ 决定课型数量
单次时长用户选（30/45/60/75 分钟）→ 决定每课型最多 N 个动作
历史水平从训练日志自动算 e1RM / 无历史→保守值
动作偏好用户排除（如膝伤不深蹲）/ 设备约束
硬约束（必须满足）软约束（尽量满足）
✓ 每个"主肌"周量 ≥ MEV × 个人系数
✓ 单次训练 ≤ 时长上限
✓ 同一肌肉两次训练间隔 ≥ 24h
✓ 用户排除的动作不出现 		~ 10 个平衡比率落在健康区间
~ 主肌优先训练频率 ≥2 次/周
~ 复合动作优先于孤立
~ 多个动作总疲劳 ≤ 单课承受
输出验收标准（系统自检）
带阶段周期的完整训练计划 ① 跑 8.2 评估：所有"主肌" ≥ MEV ✓
② 跑 11 评估：≥ 7/10 平衡比率在区间内
③ 时间检查：每课 ≤ 用户预算
④ 全部通过 → 交付给用户
⑤ 部分通过 → 进入"权衡协商"步（见 1.6.3）

1.6.2 算法逻辑（概念伪代码）

function generatePlan(inputs) {
  // 1. 算每块肌肉的目标周量（MEV × 个人系数）
  const targets = computePersonalTargets(inputs);

  // 2. 构造候选动作池（按目标 + 排除项过滤）
  const candidates = EXERCISE_DB.filter(matchesGoal && notExcluded);

  // 3. 解约束问题：选最少动作满足所有 MEV
  let movements = solveCoverageILP(candidates, targets);
  //    优先选高 fatigueCost 的复合动作（一个动作覆盖多块肌肉）
  //    每块肌肉至少有 1 个 contrib ≥ 0.5 的动作

  // 4. 分配到课型（频率分摊）
  let courses = assignToCourses(movements, inputs.frequency);
  //    Schoenfeld 2016：主肌 ≥ 2 次/周

  // 5. 检查平衡 + 时间
  let plan = { phases, courses, progressions };
  const eval = evaluatePlan(plan);

  // 6. 自检
  if (eval.mevPass && eval.balancePass && eval.timePass) {
    return { plan, status: 'ready' };
  }

  // 7. 不通过 → 协商
  return {
    plan,
    status: 'tradeoffs',
    issues: eval.issues,
    options: suggestRelaxations(eval.issues)
  };
}

1.6.3 当硬/软约束冲突时——"权衡协商"

有些约束天然冲突，不可能全满足：

  • 例：增肌目标 + 时长 30 分/次 + 6 课型 → 时间不够把 42 块肌肉都覆盖到 MEV
  • 例：增肌目标 + 上身美观偏好 → 上身/下身比天然 > 1.5（违反"客观平衡"区间）

这时系统应该明确告诉用户冲突，让用户做选择：

权衡选项影响
① 增加训练时长 30 → 45 分能覆盖到 MEV，但单次更长
② 接受部分肌肉不达 MEV（小腿/腹斜等）这些肌肉作为"维持"状态
③ 增加频率 3 → 4 次/周每次可短，但总时间多
④ 接受上身/下身比偏高对"上身美观"导向用户可接受

"协商"是设计的关键——系统不替用户做这种价值权衡，而是把权衡的代价讲清楚让用户决定。

1.6.4 计划级问题 vs 执行级问题 · 这是 2 个不同的流程

类型什么时候发现怎么处理
计划级
（结构性）		 计划生成时，系统自检就发现 ① 系统自动修补（加动作）
② 用户看不到——除非是"权衡冲突"
③ 永远不出现在「复盘→修复方案」
执行级
（偏差）		 训练 N 周后复盘，发现实际表现 ≠ 计划预期 ① "复盘 → 教练建议"
② 例：RIR 经常 ≥4 → 强度不够 → 改重量；3 周没渐进 → 减载 1 周；个人 MEV 与默认偏差 → 调系数

1.6.5 关于现有 30 节 HTML 训练计划（坦白）

当前 30节课训练计划.html 里的 W5+/W6+ 补充动作（俯卧腿弯举、坐姿提踵、侧平举升组）——本质是"计划级问题"：

  • 那个计划是手工设计的早期版本，未经过"生成→自检→修补"循环
  • 所以才需要后续的 8.3 "修复方案" 把漏洞补回去
  • 如果用 1.6.1 描述的算法生成，第一稿就应该已经包含这 3 个动作——它们不应该是"修复"，它们应该是"基础"

新 App 里的计划生成必须避免这一类计划级缺陷。所以 Wizard 第 5 步会强制运行自检，不通过就回到调整环节。

2.2 为什么是这 3 个？

  • 时间方向区分：复盘=向后（看过去）/ 计划=现在（执行中）/ 我的=超时间（资源+配置）——天然 3 分
  • 使用频率排序：计划每天/每周开 → 应居中；复盘每周/每月看 → 左；我的偶尔改 → 右
  • 认知负担最小：手指自然到中间，最常用的不需要找

「肌肉训练情况」的深度展示

不能只显示"达 MEV 的肌肉数"——要深入到每块的4 个维度：

这个数字什么意思？
胸训练量 ÷ 背训练量 = 0.52。说明你拉的量是推的近 2 倍。
为什么这是问题（或不是）？
传统建议 0.6-1.2（Cools 2007）。但你的 0.52对久坐人群其实是好纠偏——反向偏拉是 Janda 姿势学派推荐方向。
系统怎么算的？
胸 19.4 / 背 36.9 = 0.52
你该做什么？
不修，除非出现圆肩或肩痛

3.4 关键设计点

  • 计划居中：打开 App 默认在计划 tab，今日卡用红色突出，1 点击进训练
  • 动作卡三态：✓ 折叠 / ⚡ 展开输入 / ○ 折叠半透明。同时只 1 张进行中
  • 动作卡内必含 4 区：① 要点（cues 自动从 DB 加载）② 实际记录（drum picker）③ 4 维自评（具体描述选项）④ 备注
  • 所有数字 drum picker，不用键盘——避免训练时手汗输入烦躁
  • 4 维自评用具体文案：每档是"具体场景描述"（如"完整幅度末端略不稳"）而不是"较好/中"——便于训练当下快速判断
  • 训练记录子页是 Plan 子页（L2），底部 tab 仍可见
  • 所有数据点带 💡：点开 R2 弹层，教练 4 段解释
  • 复盘按 6 段模板展开：周期定位 / 当初假设 / 实际 / 一致偏离 / 教练解读 / 前瞻——所有时段同模板
  • 每块肌肉判断基于"阶段预期"而不是绝对 MEV——阶段一只期望 60% MEV，达了就 ✓
  • 计划级 vs 执行级问题严格分流：计划级 → 生成时自检（P7）/ 执行级 → 复盘里出现（R3）
  • 计划评估 P6 vs 复盘 R1 的差别：P6 = 设计层（理论上的）/ R1 = 实测（实际的）。差异本身就是反馈
  • 每周顶部有教练 1 段"这周设计目的"——让用户理解为什么

  • e1RM：weight × (1 + 0.0333 × reps)

Service Workercache static assets（HTML/CSS/JS） + offline first无网络也能查所有屏
同步暂不做（导出/导入 JSON 即可）避免引入服务器；后续可加 GitHub Gist 同步

8.3 不做的事（明确拒绝）

  • 不做服务器后端——保持纯本地，数据归用户
  • 不做账号系统——本地存储 + 备份/同步即可
  • 不做 AR/AI 教练视频——内容已重，不增加新模态
  • 不做社交/排行榜——个人工具，不是社区
  • 不做付费功能——这是个人项目

9. 总结：这套设计在解决什么问题

现有的 6+ 个 HTML 文件解决了"分析过去 + 设计未来"的内容问题，但用户旅程是断裂的——每次都要在多个文件间跳，没有统一的"今天该干什么"入口、没有跨多个时间维度的复盘。

FitLab 把这些内容整合进一个 PWA：

  • 每次打开都从"今天"开始，知道接下来 30 秒该做什么
  • 训练记录与原理学习直接相连——记录时遇到不懂的概念点过去看，看完原理跳回自己数据看怎么用
  • 多时间维度的复盘（日 → 周 → 月 → 季 → 年）让"训练 1 年"这个抽象概念落到具体可看的数据
  • 每条数据都能溯源到原理——为什么这块肌肉应该练几组、为什么这周该减载——都能从数据点击查原理

本质上是把"内容 + 数据 + 评估"的关系做成一个有机的、可探索的、个性化的学习+实践闭环，而不是 6 个独立的网页。
